Reports problems with custom rules — @rule declarations and the | invocations that use them.

Rules are how a spec suite is factored, and nothing else checks them: an invocation that matches no rule simply does nothing, silently, and a rule's text can drift away from its call sites with no signal at all.

  • GL601 — an invocation matching more than one rule. Galen picks one, and which is not visible from the spec. Easy to cause by accident, because an undecorated %{param} matches .*.
  • GL602 — an invocation matching no rule, so the line does nothing. The message names the closest declared rule when there is one.
  • GL603 — @ruleBody outside a @rule declaration.
  • GL604 — an invocation with an indented block beneath it, where the rule never invokes @ruleBody, so the block is silently ignored.
  • GL606 — a %{name: regex} capture whose regular expression does not compile, making the parameter unmatchable.
  • GL607 — a rule body using a ${...} the rule does not declare. objectName, @set variables, enclosing loop bindings and Galen's JavaScript API are all accepted.

Rules declared in JavaScript files loaded with @script are found too, by scanning them for rule("...") calls — without that, every invocation of a JavaScript-defined rule would be reported as matching nothing.
